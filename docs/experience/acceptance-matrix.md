# 知识书架体验验收矩阵

本表依据本轮 `goal-objective.md`，用于逐项核验“已有产品变得顺手、简洁、统一”。它是验收契约，不是完成报告。创建日期：2026-09-28。

## 使用方法与证据边界

- 初始状态一律为 **待验证**；它既不表示当前能力缺失，也不表示已经完成。确认需要补齐的项可改为“待实现”，不得凭代码存在直接关闭。
- 每行关闭时附证据路径、日期、提交 SHA/工作树差异、环境及样本。依赖多种证据的行必须全部具备；某一类通过不能替代另一类。
- **A — 自动化/服务实测**：实际运行的单测、集成测试、API 请求、隔离数据回读、进程重启、故障注入、DOM/状态断言。只能证明所覆盖的行为。
- **B — 真实浏览器**：在当前应用实际页面操作，记录路径、输入、截图或录像、浏览器及窗口尺寸，并观察页面与服务状态是否一致。自动操控真实浏览器属于 B，也可同时提供 A 断言；不会因此成为真实用户观察。
- **U — 真实用户观察**：目标用户按任务提示独立操作，不由执行者讲解按钮位置或产品概念；记录是否完成、在哪里犹豫/误解/求助、用户原话。执行者自己顺利操作不能替代 U。
- **M — 真实模型检查**：沿用现有模型 API，以明确样本实测连续理解与源码依据，记录问题、回答、快照及核验结果；故障替身与固定回答不得冒充 M。不要在证据里保存 Key。
- **R — 范围/方案审查**：当前差异、信息结构、文案/组件规则、前后对照、保留与调整清单。设计稿仅证明方案可审查，不能证明实现表现。
- 每个已知缺陷先保留复现/失败证据，再附修复后的同场景证据；没有复现的风险保持待验证。既有测试不能删减、跳过或放宽。
- `npm test` 通过、95 项历史检查、源码字符串匹配、单张截图都不能独立证明整个体验完成。不得把“尚未观察到问题”改写为“没有重大问题”。

证据记录统一使用：`验收项 ID｜样本与初始状态｜步骤｜实际结果｜证据路径｜代码版本/日期｜检查者/观察者｜未解决事项`。可复用同一次完整旅程的记录，但须标出每行对应的步骤。

## 固定验收背景

| 项目 | 本轮边界 |
|---|---|
| 用户 | 有基础的开发者、AI 编程用户；需要快速理解陌生项目 |
| 交付 | 本地浏览器应用，一键启动；优先当前 macOS，覆盖桌面与窄窗口 |
| 主线 | 项目源码 → 主书 → 旁注/源码核验或探索 → 用户确认生成小书 → 下次继续 |
| 数据 | 使用隔离数据；保留真实资料、生成书、`.env`、未提交改动和 `data/tmp-import` |
| API | 保留原有模型接入；模型等待、应用处理及渲染分别记录，不通过换模型证明改善 |
| 页面 | 项目从书架直接进入主书；辅助能力按需出现，不新增必经的项目管理页 |
| 必备样本 | 一个可核验的小型源码项目；一份有长代码/宽表格的主书；两种不同书皮；有旁注、历史探索、小书的回访项目；导入失败与无有效文件样本 |
| 环境记录 | 实际浏览器/版本、窗口尺寸、缩放、主题、动态效果设置、机器、代码版本、隔离数据位置；未覆盖的浏览器不能宣称已通过 |
