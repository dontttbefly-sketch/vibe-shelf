# 可递归项目书系：真实生长链设计

**状态：已确认，尚未实现**
**日期：2026-09-18**

## 1. 要解决的事情

知识书架现在能把一个项目编成一本教学书，并在阅读时生成旁注。下一阶段不把它扩成“多本书切换”或“聊天记录列表”，而是让一个项目逐渐长成一套可学习、可继续探索的书系：

```text
项目源码（事实底座）
  → 项目主书（对整个项目的连续整体讲解）
    → 自由探索对话（轻量、可回看）
      → 探索小书（从值得继续的主题长出）
        → 更深的探索小书
```

用户最终看到的地图是这套书系的可视化结果，不是第一阶段需要先做的一张空白思维导图。

## 2. 当前基础与设计约束

现有项目是“单本编译后的 HTML 阅读器 + 旁注叠加层 + 本地 Node 服务”：

- `build.mjs` 将教学书编译为单个 `public/index.html`，并注入 `window.SHELF_BOOK`。
- `public/notes.js` 与 `public/notes.css` 提供划词、旁注、追问、diff 审核与晋升正文体验，不改动原书正文结构。
- `server.mjs` 本地保存旁注并代理模型调用；项目文件目前约定放在 `data/<book>/files/`。
- GitHub Pages 只能承载静态演示；项目导入、项目级 AI 对话和数据持久化只能在本地完整模式中工作。

本设计保持这些原则：

1. 原项目源码与主书都不被 AI 静默改写。
2. AI 的内容必须由用户决定是否让它成为长期结构。
3. 书页依然以阅读为主，工具低存在感；项目内页不做密集仪表盘。
4. 用户感觉 AI “知道整个项目”，但服务端不把全部源码粗暴塞入每次提示词。

## 3. 核心对象与状态

| 对象 | 含义 | 是否长期结构 |
|---|---|---|
| 项目 | 用户导入的一份源码快照及其书系 | 是 |
| 源码快照 | 项目某一时刻的受控、可追溯源文件集合 | 是 |
| 主书 | Skill 对整个项目生成的连续整体讲解，是用户可见的主干 | 是 |
| 书内旁注 | 针对主书或小书既有内容的局部理解补充 | 是，挂在书内 |
| 探索对话 | 介于主书与探索小书之间的自由项目级追问 | 是，但轻量，不占地图正式位置 |
| 探索小书 | 一个探索主题的可继续阅读空间；其第一页来自触发它的当前问答 | 是 |
| 知识地图 | 由书与书的真实来源、父子和关联关系投影出的视图 | 后续能力 |

“采纳探索”不作为产品术语。正确的动作是**让一个问题长成一本书**：它不是审核一条答案是否正确，而是确认这个主题值得继续阅读、批注和追问。

## 4. 用户体验与信息架构

### 4.1 书架首页

首页是项目入口，而不是缺乏上下文的 AI 聊天页：

- 顶部是极简搜索／添加入口；最终支持本地文件夹与 GitHub 项目。
- 下方以书的形式陈列已经导入的项目。
- 点击一个项目进入项目内页，而不是直接跳回某本书。

第一阶段只让本地文件夹导入真正可用；数据模型预留 GitHub 来源，但不展示无法完成的伪能力。

### 4.2 项目内页

项目内页是一页安静的“项目扉页 + 小书架”，它组织但不替代阅读：

- 最醒目地展示项目主书。
- 陈列已经长成的探索小书，能看出它来自哪个主题或哪本父书。
- 保留最近的轻量探索记录，用户可以继续对话或从一条旧问答成书。
- 提供“探索这个项目”的项目级入口，不依附任何具体书。
- AI 主动给出 2–3 个值得深挖的方向；每个方向仅显示题目与依据，不自动创建书。

### 4.3 具体书页

主书和探索小书使用同一套阅读器能力：阅读、划词旁注、旁注追问、底部探索。顶部以简洁面包屑说明位置，例如“项目内页 / 主书 / 部署与运行环境”。

书内划词追问解决“书正在讲、但读者尚未理解”的局部问题；书底部的探索解决“这本书还没有讲到、但我想基于项目继续深挖”的新主题。两者不能混为同一类旁注。

## 5. 探索与成书流程

```text
主书或项目内页
  → 进入探索对话
    → 普通问答：保存为轻量、可回看的探索记录
    → 明确的“深挖／成书”意图，或接受 AI 的成书建议
      → 当前问答成为探索小书的第一页／种子
      → 用户进入该小书，继续阅读、批注、追问或再次探索
```

探索对话具有项目级源码上下文：

- 从书底部发起时，当前书、章节和阅读位置是额外上下文，而不是唯一限制。
- 从项目内页发起时，问题直接面向整个项目。
- 普通探索记录可在之后继续追问，也可从任一问题触发成书。
- AI 可建议一个新主题与主书、已有小书的关联；用户确认才落入长期书系。没有合适关联时，它是项目级独立探索小书。

探索小书不强制在成书动作中生成一整本长文。当前问答是第一页，后续内容通过读者的真实追问自然生长。

## 6. AI 上下文、来源与用户控制

项目导入时，服务端保存一份本地源码快照并建立文件索引。回答问题时按照问题、当前书、当前探索对话检索相关片段，并连同必要的书内上下文交给模型。

这让用户获得“AI 默认理解整个项目”的体验，同时避免每次传输全部源码。每个回答应保留其主要来源文件、代码范围和源码快照版本；阅读时来源保持低打扰，需要时可展开查看。

AI 的权限边界：

- 不修改原项目文件。
- 不修改主书正文。
- 不自动创建探索小书。
- 只在用户明确发起成书，或用户接受 AI 建议时创建探索小书。
- 模型失败时保留探索记录并允许重试，不制造空书。

## 7. 数据与模块边界

将现在按单个 `book` 组织的数据升级为项目作用域。建议的本地结构：

```text
data/projects.json
data/projects/<projectId>/
  project.json                 # 名称、来源类型、导入时间、当前快照、主书 ID
  source/<snapshotId>/         # 受控源码快照
  file-index/<snapshotId>.json # 路径、语言、哈希、可检索片段信息
  books/<bookId>/
    book.json                  # 类型、标题、父书、来源会话、快照、关联来源与正文来源
  explorations/<sessionId>.json
  notes/<bookId>.json

public/projects/<projectId>/books/<bookId>/index.html
                               # 可重新生成的独立阅读产物
```

关键关系：

- `book.kind` 为 `main` 或 `exploration`。
- 探索小书保存 `parentBookId`（可为空）、`originExplorationId`、`sourceSnapshotId` 和来源引用。
- 探索会话保存 `projectId`、可选的 `originBookId`、消息、来源引用和状态（可继续／已成书／归档）。
- 每本书的旁注独立保存，避免主书、小书和不同版本互相污染。

模块演进边界：

- `build.mjs` 从“覆盖唯一 `public/index.html`”变为“为一个指定项目书生成独立阅读产物”，并正确解析各书页面的共享资源路径。
- `public/notes.js` 和 `public/notes.css` 继续作为阅读层；运行时上下文升级为 `projectId + bookId`，而不是只有 `book` 字符串。
- `server.mjs` 增加项目、导入快照、书、探索会话和项目级问答接口。可按职责拆分模块，但仍保持本地零依赖运行。
- 新增首页与项目内页的轻前端层；它们调用项目级 API，不把项目结构硬编码在静态页面中。

现有 PUPKIT 示例迁移为一个示例项目，现有旁注数据在迁移时按主书归位，不能丢失。

## 8. 源码更新与隐私

第一阶段是本地、手动刷新的模式：

1. 用户显式选择要导入的本地文件夹。
2. 系统只复制通过忽略规则、文本／二进制判断、文件数量和体积限制的文件，形成受控快照。
3. 用户主动刷新时创建新快照，不覆盖旧快照。
4. 旧书、旧探索和旧答案继续指向原快照；页面可提示它们不是基于最新源码，但绝不静默改写。

未经用户显式选择，网页不请求服务器读取任意本地路径。源码默认留在本地；发给配置模型端点的是为当前问题选出的必要片段，并在产品内保留可见来源。

## 9. 第一阶段范围

**必须完成的真实闭环：**

1. 导入一个本地项目并建立项目记录／源码快照。
2. 为该项目登记一部由现有 Skill 生成的主书，并将它编译为该项目的独立阅读页。第一阶段不把“自动生成整本主书”做成应用内后台任务。
3. 从项目内页和书底部开始、保存、恢复探索对话。
4. 将一次探索的当前问答长成探索小书。
5. 用既有阅读器能力阅读、批注、追问该小书。
6. 回到项目内页，看见主书、探索小书与最近探索记录。
7. 对一个真实项目走通上述流程，并保证现有单书旁注功能不回归。

**明确后置：**

- GitHub 的真实导入、私库认证与同步。
- 云端账户、多设备同步和协作。
- 自动监听本地源码变化。
- 可拖拽、全屏的大型知识地图。
- 自动把 AI 生成内容写回源码或主书。

## 10. 失败行为与验收

| 情况 | 必须行为 |
|---|---|
| 导入失败、非法路径、超限或二进制文件 | 不创建半成品项目；给出具体原因 |
| 模型请求失败 | 保留探索记录和原始问题；可重试 |
| 成书生成失败 | 不出现空小书；对话仍可继续或重试成书 |
| 源码刷新 | 新建快照；既有书和问答不可被改写 |
| 旧单书数据 | 迁移后仍可打开原书与旁注 |

验收以真实用户路径为准，而不是只看页面存在：从一个真实本地项目出发，用户必须能走到“主书 → 探索 → 小书 → 回到项目内页”，并能在小书中使用旁注与进一步探索。

## 11. 后续演进

当多个项目、主书和探索小书已有真实关系后，再增加知识地图。它读取 `parentBookId`、来源会话和关联来源生成视图；地图不成为内容的唯一存储方式。

GitHub 导入接入同一项目与快照模型：公开仓库先固定 commit，私库再单独设计授权和凭证边界。这样第一阶段的数据不会因来源扩展而迁移。
