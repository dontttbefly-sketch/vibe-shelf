## 1. 北极星：这个产品最终要帮用户完成什么

**已确认**：知识书架帮助用户把自己的项目读明白，而不只是把代码文件交给聊天机器人。

用户导入一个项目后，先得到一部关于整个项目的连续讲解书；读到不懂、好奇、或想深挖的地方时，可以在同一个项目语境里继续问 AI。真正值得继续的方向，才由用户决定沉淀为一本可阅读、可做旁注、可继续追问的小书。随着主书、小书和探索积累，项目会自然长成一套可回看的知识结构；未来的可视化地图只是这套真实结构的呈现，不是先画一张空的思维导图。

产品服务的学习不只限于“代码怎么写”，还包括项目架构、运行机制、领域知识、配置、部署与其他与项目有关的理解问题。

### 用户成功时的感受

> “我不是在翻文件，也不是在存一堆聊天记录。我先读懂了这个项目的大方向；遇到问题时，它知道我指的是哪一段、哪份源码；值得继续的理解路径会留下来，下一次我能从那里接着读。”

## 2. 已确认的产品判断

### 2.1 源码与主书的关系

| 判断 | 要求 |
|---|---|
| 源码是事实底座 | AI 的理解、解释和来源都必须以项目源码快照为依据。源码不是可被 AI 静默改写的材料。 |
| 主书是读者看到的主干 | 用户第一次进入项目，不应被迫从原始目录树开始。由 Skill 生成的整体讲解书是用户可读、连续、带叙事的主线。 |
| 主书不是“泛泛概述” | 它应讲清项目整体如何工作，并为后续问题提供上下文，而不是只列模块名称。 |
| 文件树不是默认第一屏 | 文件目录、架构分类和源码定位是可追溯的事实层，不替代第一阅读体验。 |
| 主书与源码可互相追溯 | 主书、小书和答案需要能够回到相关源码文件／范围；但来源信息默认低打扰，用户需要时再展开。 |

换句话说：**源码是事实上的根，项目主书是体验上的主干。** 这两个概念不能再被混成“必须先看目录树”。

### 2.2 书内旁注与书外探索必须分开

| 场景 | 用户真正要做的事 | 正确产物 |
|---|---|---|
| 在一句、一个段落或一段代码上划词提问 | 听懂当前正文正在讲什么 | 书内旁注／局部追问；挂在当前书内。 |
| 在书底部提问 | 探索正文尚未讲到、但与当前项目有关的新方向 | 一次独立的项目级探索对话；不插回正文，也不伪装成旁注。 |
| 在主书底部或小书底部继续提问 | 跳出当前正文段落，理解整个项目或寻找新的深挖方向 | 一次独立的项目级探索对话；可带当前书、章节和阅读位置作为额外上下文。 |

**已确认**：书底探索不是“给这一篇补内容”，而是另起一种探索需求。它可以和主书有关，也可以是新的项目级方向。

### 2.3 “采纳探索”真正表示什么

**已确认**：不使用“采纳一条答案”作为核心产品心智。更准确的动作是：

> **让这个问题长成一本书。**

它的含义不是把 AI 回复塞进主书正文，也不是把聊天记录标星；而是用户确认“这个主题值得在以后继续读、继续做旁注、继续追问”。

因此：

- 普通问答先保留为轻量、可回看的探索记录；
- AI 可以说明为什么某个方向值得深挖，并建议它与主书／已有小书的关系；
- 只有用户明确点击“让这个问题长成一本书”或确认 AI 的建议时，才创建探索小书；
- 当前问答是小书的第一页／种子，而不是强行一次生成一篇长文；
- 小书之后通过真实的阅读、旁注、追问自然生长；
- 不合适挂到任何章节的主题可以成为项目级独立小书；不能硬塞回某一段正文。

**【决策 2026-09-20】小书种子（第一页）的形态（暂定）：** 用户确认成书时，AI 把该次问答**整理成一篇有标题、有结构、带源码引用的短文**作为小书第一页；之后通过阅读、旁注、追问自然追加。此决策为**暂定**（用户标注“不太确定”），实现时种子生成必须做成**独立可替换的模块**，先跑起来再验证。备选形态：对话原样 / 标题空壳。

### 2.4 探索中的“模糊状态”是合理状态

**已确认**：当用户从主书探索一个新方向时，他常处于“主书和潜在小书之间”的模糊状态。产品不能要求用户在开口前先决定它是不是一本书。

探索状态必须允许两种结局：

1. 问题被回答，用户继续或结束；它仍是可回看的轻量探索。
2. 某次问答显示出持续价值；用户再决定让它长成一本小书。

这解释了为什么“先对话、后成书”比“先让用户创建一篇新文档”更符合真实学习过程。

## 3. 核心对象与关系

```text
项目源码快照（事实、可追溯）
  └─ 项目空间
      ├─ 项目主书（对整体项目的连续讲解；读者主干）
      │   ├─ 书内旁注（解释当前正文）
      │   └─ 书底探索（新的项目级方向）
      ├─ 项目级探索（不依附具体书）
      ├─ 轻量探索记录（可恢复、可继续追问）
      └─ 探索小书（由某次探索问答明确长出）
          ├─ 书内旁注
          └─ 进一步探索／更深的小书
```

| 对象 | 用户可见含义 | 必须保存的关系 |
|---|---|---|
| 项目 | 一套独立的学习空间 | 来源、当前源码快照、主书、所有书与探索。 |
| 源码快照 | 某一次被导入／刷新的项目事实版本 | 创建时间、来源、文件索引；旧内容仍指向旧快照。 |
| 主书 | 项目的整体讲解、可读主线。**【决策 2026-09-20】可替换（重新生成即覆盖）**；旧旁注按选区文本尽力重锚到新主书，失锚旁注标记“失锚”状态但不删除，用户可清理。 | 项目、使用的源码快照、来源文件。 |
| 书内旁注 | 对现有书页的局部理解补充 | 书、章节／选区、可选源码来源。 |
| 探索会话 | 主书和小书之间的自由探索过程。**【决策 2026-09-20】“轻量探索记录”不是独立对象，未成书只是会话的状态**（未成书 / 已长成书）。 | 项目、可选发起书／章节／阅读位置、消息、来源、状态。 |
| 探索小书 | 一个可继续阅读的探索主题。**允许递归**：小书内可再探索、再长出更深的小书，内页以“来自哪本父书”标识层级，不做深度限制。 | 项目、可选父书、来源探索／回答、源码快照、来源引用。 |
| 知识地图 | 书系关系的可视化视图 | 只能由真实的父子、来源和关联关系投影出来。 |

## 4. 用户旅程与信息架构

### 4.1 两层主流程：书架首页 → 主书阅读页

```text
书架首页
  → 主书阅读页（项目的默认界面）
      → 书底探索
      → 探索小书阅读页
      → 更深的探索与小书
```

| 层级 | 用户此刻的目的 | 页面必须回答的问题 |
|---|---|---|
| 书架首页 | 开始一个新项目，或回到已经导入的项目 | “我从哪里开始？我已有的项目在哪里？” |
| 阅读页 | 沉浸式阅读一部具体的书 | “这本书正在讲什么？这里不懂时怎么问？想往外深挖时怎么开始？” |

**已确认（2026-09-23 覆盖旧三层判断）**：项目内页不再是核心承接层。项目的“空间感”由主书底部探索、小书关系、旁注和未来知识地图共同承载；第一入口必须是主书本身。用户进入项目后，应感觉自己已经坐在这本项目书里，而不是先到一个管理面板。

### 4.2 首次进入与已有项目

1. 用户从首页看见一个清楚、可操作的新项目入口。
2. 用户可从本地文件夹开始，未来也可从 GitHub 项目开始。
3. 用户选择本地文件夹后，应用内后台生成项目主书；生成过程要有进度反馈。
4. 导入成功后直接进入项目主书，主书就是项目默认首页。
5. 已有项目以“书”的形式陈列在首页下方；用户点击项目小书，直接打开该项目主书。

### 4.3 从阅读到探索再到小书

```text
读主书／小书
  ├─ 划词 → 局部旁注 → 解释当前内容
  └─ 到书底提问 → 项目级探索会话
                         ├─ 继续问／稍后恢复（轻量记录）
                         └─ “让这个问题长成一本书” → 新探索小书 → 继续阅读
```

探索入口优先放在主书／小书底部。没有当前章节上下文的项目级探索，后续可由首页或知识地图补充，但不再以项目内页作为默认入口。

### 4.4 主书内的项目承接

- 项目主书：是理解整个项目的第一入口，也是点击项目后直接进入的界面。
- 书底探索：承接“这本书之外还想知道什么”的项目级问题。
- 已经长成的探索小书：应在主书底部或未来知识地图里被看见，能识别其来源主题、父书或探索会话。
- 最近探索：轻量、可回看、可续聊，也可从某条旧问答再次成书；第一阶段可先在书底探索区域承接。
- AI 推荐的 2–3 个值得深挖方向：仅展示标题和推荐依据；**不自动创建书**。
- 返回书架：只是辅助逃生口，固定在顶部右侧；视觉上应低存在感，避免打断用户在项目里深挖。

## 5. AI 的项目理解、边界与可信度

### 5.1 用户体验要求

**已确认**：在同一个项目里对话时，AI 默认知道项目里的文件、源码与当前上下文。用户不应反复手动挑选文件来解释“我说的是哪个东西”。

这不等于每次把全部源码发给模型。正确体验是：

- 导入项目时保留一份受控源码快照并建立文件索引；
- 每次根据问题、当前书、探索会话和阅读位置检索必要的源码片段；
- 回答保存主要来源文件、代码范围和快照版本；
- 用户需要时能看见“这段解释依据什么”，平时不被来源面板打断阅读；
- 老书、老问答与新快照并存，不会因源码刷新被悄悄重写。

**【决策 2026-09-20】源码检索策略（第一阶段）：** **全量直塞**——源码快照全量进入 AI 上下文，设文件数与单文件大小上限（超限提示用户裁剪）。不引入关键词排序或向量检索，保持零依赖；上限值实现时按主流模型上下文窗口标定。

### 5.2 AI 不得越过用户的边界

| 边界 | 必须行为 |
|---|---|
| 项目源码 | AI 不直接修改。 |
| 项目主书 | AI 不直接改写正文。 |
| 探索小书 | 不自动创建；必须由用户发起或确认建议。 |
| 普通对话 | 默认只是可恢复的探索记录，不膨胀成长期知识结构。 |
| 失败 | 模型失败保留问题和会话，允许重试；绝不制造空小书。 |
| 推荐 | AI 的深挖建议应带简短理由和可追溯依据，而不只是抛出标题。 |

### 5.3 隐私与版本边界

- 本地项目优先；用户显式选择文件夹后才读取和导入文件。
- 浏览器或网页参数不得让服务端读取任意本机绝对路径。
- 发送给模型的是当前问题所需的相关片段，而不是默认上传整仓库。
- 用户手动刷新源码时应创建新快照；旧书、旧探索、旧旁注继续引用其原始快照。

## 6. 首页：首屏是“开始理解一个项目”的入口，不是大标题海报

这一节专门记录用户对官网／书架首页的明确反馈。后续视觉改版必须逐条对照，不得只把颜色或字号换一下。

### 6.1 首屏唯一优先级

**已确认**：新用户第一眼必须清楚知道“这里可以开始读懂一个项目”，并且马上看见自己在哪里输入／从哪里开始。

首屏的唯一主动作是：**开始一个新的项目理解过程。**

因此：

- 中央开始框／输入框必须是首屏最主要、最大、最高对比的视觉元素；
- 不能让巨大的标题或说明文字把输入框推到首屏下方；
- 输入框必须像一个真正可点击、可输入的控件，有明确的深色边界／容器和焦点反馈；
- 用户不需要读很多宣传文案才能理解下一步；布局、对比、留白和动作层级本身要说明页面用途；
- 已生成项目不应占用中央开始区，它们在下方书架中承接“继续阅读”。

### 6.2 新项目的入口语义

**【决策 2026-09-20】已确认的入口语义：**

1. **本地文件夹（主要方式）**：用户上交项目文件夹 → 进度条 → **后台调用 Skill（经用户 API）生成主书 HTML** → 完成通知。主书是应用内生成的，不再要求用户自备主书文件。
2. **GitHub 项目**：来源方向，第一阶段未实现，诚实标注“即将开放”。
3. **自由输入**：**第一阶段不做无源码主题空间**。中央输入框 = 给项目起名 + 选择来源的导入向导第一步；自由领域输入标记“即将开放”（FR-13 保持后续）。

**生成流程（异步任务模型）：** 项目记录先创建（状态 = 主书生成中）→ 首页开始框显示进度 → 生成成功直接进入主书阅读；失败可重试，不留半成品。旧实现“用户自备主书 HTML”仅为过渡现状，不是目标。

### 6.3 首页信息层级

| 层级 | 内容 | 首屏优先级 |
|---|---|---|
| 1 | 中央开始框：输入／表达“我想读懂什么” | 最高；首屏必须可见。 |
| 2 | 两个项目来源选择：本地文件夹、GitHub 项目 | 紧随输入，不和已有项目争夺注意力。 |
| 3 | 当前本地导入必须补齐的主书选择与开始动作 | 只在用户进入相应流程后清楚出现，不应成为突然冒出的隐藏要求。 |
| 4 | 已有项目书架 | 下沉到页面下方，用于返回／继续，不替代新项目入口。 |
| 5 | 解释性文案、版本说明、辅助链接 | 低优先级；只在有助于决策时出现。 |

### 6.4 不可接受的首页表现

以下是已明确被用户否定的方向，后续设计不得回退：

- 巨大标题占满屏幕，真正的输入区只能滚动后看到；
- 输入控件灰、弱、没有边界，让用户不知道能否点击或在哪里输入；
- 通过堆很多口号、说明文字、标签来解释网站，而不是用视觉层级说清楚；
- 模块、卡片、边框堆叠造成嘈杂和不知从何开始；
- 主页面整体偏灰、浑浊、无明确焦点；
- GitHub 功能尚未实现却表现得像已可用；
- 所有点击都没有即时反馈，页面像静态展示图而不是一个可操作的产品入口。

## 7. 视觉与动效要求

### 7.1 视觉气质

**已确认：**

- 官网第一眼应该简约、安静、清晰；
- 整体要比“灰色仪表盘”更明亮，避免沉闷的灰；
- 视觉要有设计语言，但不能靠装饰性噪音、过多卡片或大段文案堆出来；
- 页面既是学习工具，也应有“打开一本自己的项目书”的温度；
- 阅读页仍以内容为主，工具退后；决定性操作（例如开始导入、长成一本书）必须清楚、可见。

可沿用现有纸面／墨色／粘土的基础语义，但每一个颜色和边界都必须服务于层级，而不是为了“复古”或“AI 感”。

### 7.2 动效不是装饰，必须表达状态

**已确认：页面需要动效。** 但动效的任务是让用户知道“哪里能操作、我刚刚做了什么、下一步发生了什么”，而不是持续吸引注意。

| 时机 | 动效／反馈必须传达的事 |
|---|---|
| 首次进入 | 建立从页面到中央开始框的注意力顺序，不用夸张标题压住操作。 |
| 输入框聚焦 | 明确“现在可以输入”，并让开始区成为当前操作焦点。 |
| 悬停／按下按钮 | 明确可点击与已经接收到操作。 |
| 选择本地文件、主书或来源 | 明确已选择什么、下一步还缺什么。 |
| 导入、加载、失败、完成 | 让用户看到过程与结果，不能静默等待或只换一行模糊文字。 |
| 探索建议／长成书成功 | 说明一条问题正在从临时对话变成长期阅读对象。 |

动效实现约束：

- 只使用 `transform`、`opacity`、`clip-path` 等合成层友好的属性；
- 尊重 `prefers-reduced-motion`；
- 不使用持续的装饰性循环动效；
- 不用 `filter: blur()` 作为展开／删除动效；
- 焦点、选中、按下和完成都需要有可感知但克制的反馈。

### 7.3 首页视觉验收准则

- 在桌面首屏中，不滚动即可看见并理解中央输入／开始区。
- 在窄屏中，开始区不横向溢出，也不能被巨大标题挤出第一阅读区域。
- 键盘聚焦输入框、来源选择、文件选择与开始按钮时，有清楚的焦点指示。
- 不只靠颜色表达“已选择／错误／即将开放”；文字或图标语义也要明确。
- 已有项目书架视觉上明显低于“开始一个新项目”的首屏主动作。

以下内容是对当前 `codex/recursive-project-books` 分支的静态检查结果，用来防止后续任务把“设计愿望”误报为现成功能。

### 10.1 已观察到的能力

## 11. 非功能与实现约束

这些约束保护已经形成的阅读体验，不是可自由牺牲的技术细节。

- 阅读器的旁注是对原书的叠加，不能修改宿主正文 DOM 结构或原书样式。
- 主书和探索小书应是独立阅读页，避免不同书的内联样式互相污染。
- 旁注与探索必须按 `projectId + bookId` 隔离；不同项目、主书和小书不能串数据。
- 静态演示模式可保留阅读和本地旁注降级；项目级 AI 探索／成书必须明确提示需要本地完整服务，不能假装成功。
- 高风险 AI 写入必须经过用户确认；当前范围内不允许写回源码或主书正文。
- 首页和阅读页应各自职责单一：首页负责开始和继续，阅读页负责项目理解、旁注与探索；项目页不再承担主流程。

## 12. 验收标准

### 12.1 产品闭环

- [ ] 从一个真实本地项目出发，用户能完成“导入 → 主书 → 探索 → 小书 → 回到主书／书架”。
- [ ] 主书作为项目整体讲解的首个阅读入口清楚可见；用户不需要先理解文件目录。
- [ ] 书内划词问题不会变成项目级探索；书底探索不会被插回当前正文。
- [ ] 普通探索可以回看和续聊，但不自动膨胀成书。
- [ ] 用户明确确认后，一条探索回答只会长成一本对应小书；主书正文保持不变。
- [ ] 小书可独立阅读、做旁注、再探索；返回主书或书架后能看见它的来源与存在。
- [ ] 每个项目内的 AI 回答有可追溯的源码快照与必要来源，旧内容不随刷新被静默改写。

### 12.2 首页与视觉体验

- [ ] 第一次打开首页，用户无需阅读长段文案，就能判断这是“帮助我读懂项目”的入口。
- [ ] 中央开始框在首屏清楚可见，是最高优先级的可交互元素；输入位置、可点击性和键盘焦点都明确。
- [ ] 本地文件夹与 GitHub 是清楚的来源选择；未开放的 GitHub 不伪装为成功。
- [ ] 已有项目以书架方式处于下方次级位置，点击后直接进入项目主书。
- [ ] 输入、选择、点击、加载、成功与失败都有克制而可感知的反馈；减少动效设置下仍可正常完成任务。
- [ ] 页面不通过巨型标题、灰雾背景、卡片堆叠或文字噪音来制造“设计感”。

### 12.3 安全与恢复

- [ ] 用户没有显式选择本地文件夹时，服务端不会按网页传入路径读取本机文件。
- [ ] 导入失败不留下半成品项目；模型失败不丢失探索问题；成书失败不出现空书。
- [ ] 旧旁注和既有单书阅读体验不回归。
