# 源码教学书生成器

## 何时用

用户手上有一个**已经写完的项目**，并希望「读懂它」而不是「新建它」。典型信号：

- "基于这个项目写一本教学书 / 代码讲解"
- "慢慢带我读完这个项目的代码"
- "讲讲我在页面上看到的东西是怎么用代码做出来的"
- "我要完全掌握这个项目的前端/后端代码"

**不适用**：从零教语言语法、API 速查、代码审查（review 找 bug）。

## 核心教学法（这是本 skill 的灵魂）

不是「按文件顺序讲代码」，而是 **从可见结果倒推代码**：

```
你在页面上看到的  →  哪一段代码做出来的  →  这背后叫什么名字  →  它在哪会失效
```

每章固定五段，**顺序不可调**：

| 段 | 内容 | 为什么必须有 |
|---|---|---|
| 你看到的 | 先描述效果/现象，让读者有画面 | 建立"我要解释的是这个"的锚点 |
| 代码 | 贴真实源码，不简化掉关键细节 | 可信度来自原样引用 |
| 知识点 | 这行代码的通用概念叫什么 | 让读者能迁移到别的项目 |
| **局限** | 这个写法在哪会顶不住 | **教程最常跳过、但对读者价值最高的一段** |
| 小结 | 3~5 条要点 | 便于回看 |

**"局限"这一段的写法**：不要泛泛说"性能可能有问题"。要给出可验证的具体事实，例如：
- grep 全项目得出「某属性出现 0 次」→ 指出这是个真实遗漏
- 指出项目内部的**自相矛盾**（某处违反了自己定的规范）
- 说清"如果项目规模涨 10 倍，这里会怎样"
- 给出工业界的替代方案，并说明它解决了什么问题

引用行号（`app.js:762`）能大幅提升可信度——但**必须先用 grep 验证行号真实存在**，不要凭印象写。

## 工作流

### 阶段 1 · 调研（不能跳）

1. **摸清规模**：`wc -l` 统计每个文件行数，`find` 看目录结构。
2. **读完核心逻辑文件**（JS/py 等），大文件（>2000 行）只读关键函数。
3. **定位样式文件的关键锚点**：`grep -n "^\.class-name\|^:root\|--var-name" styles.css`，不要通读 3000 行 CSS。
4. **验证每一个准备写进书里的断言**。用 grep 计数验证"出现 N 次""0 次""只用了一次"。这一步决定了这本书是"可信"还是"听起来对"。
5. **主动找两类"硬证据"**，它们比任何泛泛的评论都有价值：
   - **死代码**：把代码里所有选择器（`qs("…")` / `qsa("…")` / `closest("…")`）提取出来，逐个去 HTML/CSS 里验证是否匹配得到元素。**匹配 0 个 = 一段从没跑过的代码，而且控制台零报错**——这是"防御性写法吞掉了错误可见性"的完美教材。
   - **反向异常**：某属性"有读取点、没有生产点"、某函数"被调用但选择器为空"、某变量"声明了但 `var()` 从未引用"。这类行是 bug 的指纹，一眼就能讲透。

### 阶段 2 · 规划章节

按"页面上可见的区块"切章，**不要按文件切**。一个参考骨架（约 20 章）：

- 第一篇 地基：文件地图 / 设计令牌与全局重置 / 语义化
- 第二篇 结构：两种钩子（class vs data-*）/ 无障碍 / 表单与按钮
- 第三篇 外观：CSS 三根支柱 / 用代码画图形 / CSS 变量做桥 / 响应式
- 第四篇 行为：结构总览 / 数据层 / 状态层 / 渲染循环 / 事件委托 / 各业务模块
- 第五篇 边界：架构复盘 / 局限与前后端边界
- 附录：术语表 / 属性全表 / 函数索引 / 自查清单

目录里**把未写的章节也列出来**并标注"待写"——让读者看见全貌，也让你自己下轮知道写什么。（全部写完后记得一次性去掉这些标记。）

**长附录必须用脚本生成，不要手写。** 像"69 个属性全表""42 个函数索引"这种，手写必错且改不动。做法：审计脚本顺手把结果写成 TSV（`属性名 \t dataset名 \t HTML次数 \t JS次数 \t 读取次数`），再用第二个脚本读 TSV 生成 `<tr>` 拼进 HTML 分片：

```js
rows.map(r => `<tr><td><code>${r.name}</code></td><td><code>${r.camel}</code></td>
  <td>${r.h}</td><td>${r.jp}</td><td>${r.reads}</td><td>${r.reads === 0 ? "⚠️ 只生产不消费" : "JS 使用"}</td></tr>`
).join("\n");
```

好处：数字与正文同源（不会出现正文说 12、附录列 11 的矛盾），改口径只需重跑一次。

⚠️ 生成器里写中文文案时，**不要把英文双引号 `"` 嵌在中文引号里**（`"疑似想做"好清洁"筛选条件"` 会直接语法报错）——中文正文一律用 `「」`。

### 阶段 3 · 生成 HTML

单文件自包含，**不依赖任何 CDN**（离线也能看）。骨架见 `references/book-template.md`。

### 阶段 4 · 校验与预览

1. 标签配对校验（脚本见 `references/verify.md`）
2. 高亮逻辑验证（同上，必须跑，否则代码块可能显示错乱）
3. headless Chrome 截图抽查
4. `present_files` 打开给用户看

### 阶段 5 · 分批交付

一次写 3~4 章，写完就交付。用户"慢慢读"，你不用等全书完成——每轮追加即可。

**⚠️ 分批追加的头号事故：拼接脚本不幂等。**

分片（`/tmp/ch21.html` 等）+ 锚点插入是很自然的做法，锚点通常选 `        </section>\n      </main>`。问题是：**合并之后这个锚点依然存在**（新内容的最后一个 `</section>` 紧跟着 `</main>`），所以"断言锚点唯一"的守卫会照样通过，重跑一次就把整批内容插进两遍。

最低要求：插入前先断言**目标 id 尚不存在**，而不是断言锚点唯一。

```js
if (src.includes('id="ch21"')) throw new Error("第 21 章已存在，脚本已执行过");
```

**补救办法（真发生了再删很麻烦，用整段重建最省事）**：

```js
// 头 = 第一处新增标记之前（即"干净的老内容"）
// 尾 = 最后一个 </main> 之后（footer + script + </html>）
// 中间整段丢弃，再按正确顺序重新拼装
const head = src.slice(0, src.indexOf(CH21_MARK));
const tail = src.slice(src.lastIndexOf("      </main>\n"));
fs.writeFileSync(book, head + ch21 + appA + appB + appC + appD + tail);
```

同时注意：**分片文件与"已合并的正式文件"会分叉**。如果合并后又对正式文件做了批量补丁（例如给某些表格加 `numcol` 类），重建时会用旧分片覆盖、**补丁全丢**（只有写在 `<head>` 里的 CSS 规则因为来自 head 而幸存）。所以**重建之后必须重跑补丁脚本并逐项复核计数**。

另外，命名分片时要留意**交付顺序**：如果附录 A 和 C/D 写在一个文件里、附录 B 单独一个文件，拼接时很容易写成 `ch21 + appB + appACD`，结果附录 B 跑到 A 前面。**合并后用注释标记把顺序打印出来核对**：

```js
[...src.matchAll(/<!-- =+ (.+?) =+ -->/g)].forEach((m, i) => console.log((i+1) + ". " + m[1]));
```

## 关键技术配方

### 配方 1 · 无依赖的轻量代码高亮（重要）

只给注释和字符串上色，就足够"看起来专业"，且零风险。

```js
document.querySelectorAll("pre code").forEach((block) => {
  let text = block.textContent
    .replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;");
  text = text.replace(
    /(\/\/[^\n]*|\/\*[\s\S]*?\*\/|&lt;!--[\s\S]*?--&gt;)|("[^"\n]*"|'[^'\n]*')/g,
    (m, c, s) => (s ? '<span class="c-st">' + s + "</span>" : '<span class="c-cm">' + m + "</span>")
  );
  block.innerHTML = text;
});
```

**必须单遍扫描（一个正则 + 分支）**。如果先替换注释、再替换字符串，第二步会匹配到第一步插入的 `<span class="c-st">` 里的引号，把标签本身也染色，输出彻底坏掉。

要点：
- 先 `textContent` 取出原文（此时 HTML 实体已解码），再转义回去，最后写 `innerHTML`
- HTML 注释分支写成 `&lt;!--[\s\S]*?--&gt;`（因为此时 `<` 已被转义）
- 中文不受 `"` `'` 影响；中文引号「」不会误匹配
- 只在行内出现奇数个单引号时（如英文 `don't`）可能漏配，代码块里极少见，可接受

### 配方 2 · 代码块样式

浅底 + 左侧彩色条，比深底更适合与正文混排：

```css
pre {
  background: #fffdf7;
  border: 1px solid var(--line);
  border-left: 3px solid var(--lilac);  /* 左侧色条是视觉锚点 */
  border-radius: 8px;
  padding: 16px 18px;
  overflow-x: auto;
}
pre code { white-space: pre; font-size: 12.5px; line-height: 1.72; }
.c-cm { color: #849690; font-style: italic; }  /* 注释：灰绿斜体 */
.c-st { color: #a8471f; }                       /* 字符串：棕红 */
```

### 配方 3 · 表格列宽（本配方已被实测修正，请勿再抄 `table-layout: fixed`）

长文本列会被挤成竖排（每行一个字）。**但不要用固定百分比列宽去解决——那会在表格形态多样时反噬。**

第一版用的是这套（**已弃用**）：

```css
/* ❌ 不要用：82 张表里 2 列 6 张、3 列 35 张、4 列 40 张、6 列 1 张，
   固定百分比无法同时适配；而且"长文本在第 3 列"的 4 列表会被挤成 15% */
.kv { table-layout: fixed; }
.kv th:nth-child(1) { width: 13%; }
.kv th:nth-child(2) { width: 25%; }
.kv th:nth-child(3) { width: 12%; }
.kv th:nth-child(4) { width: 50%; }
```

**正确做法：交给浏览器自动分配，只对"确定很短"的列加 nowrap 工具类。**

```css
.kv { font-size: 13.5px; width: 100%; table-layout: auto; }
.kv th, .kv td { white-space: normal; word-break: break-word; vertical-align: top; padding-right: 10px; }
.kv th:last-child, .kv td:last-child { padding-right: 0; }
/* 首列是编号/短标签的表格：加 class="kv numcol" */
.kv.numcol th:first-child, .kv.numcol td:first-child { white-space: nowrap; word-break: keep-all; }
/* 单个单元格不想折行时：加 class="nowrap" */
.kv .nowrap { white-space: nowrap; word-break: keep-all; }
```

用法：`<table class="kv numcol">`，只用在首列是**数字编号或 2~3 字短标签**的表格上（如附录的函数索引、自查清单、步骤表）。

⚠️ **绝对不要写 `.kv th:first-child { width: 1% }`**。这个"shrink-to-fit"技巧**必须**配合 `white-space: nowrap`；单独使用时它会把首列强制成 1% 宽，于是 `HTML` 竖成 `H/T/M/L`、`属性名总数` 一字一行，比原来的问题更糟。实测踩过。

**判断依据**：先用脚本统计文档里所有 `<th>` 的文本长度分布和列数分布（见 `references/verify.md` 的表结构扫描）。如果列数种类 ≥ 3 种、且存在"长文本不在最后一列"的表格，就必须用 `auto`。

### 配方 4 · 配色与源项目呼应

**教学书用被讲解项目自己的设计令牌配色**——这本身就是个教学细节（读者会注意到"书和站点是一套颜色"）。

做法：读源项目的 `:root`，把 `--ink` / `--paper` / 强调色原样搬进书的 CSS。

### 配方 5 · 四个必有的交互

| 功能 | 实现 |
|---|---|
| 顶部阅读进度条 | `scroll` 事件算 `scrollY / (scrollHeight - innerHeight)` |
| 目录高亮当前章 | `IntersectionObserver`，`rootMargin: "-72px 0px -70% 0px"` |
| 章节锚点不遮标题 | `.chapter { scroll-margin-top: calc(var(--header-h) + 24px) }` |
| 目录可折叠（移动端） | 940px 断点下 `flex-direction: column` + 目录改静态 |

## 阶段 6 · 升级成书架（书做完之后才考虑）

书交付后用户常会提"想做成一个能沉淀多本书、能改、能挂笔记的平台"。此时读
`references/shelf-and-marginnote.md`。三个必须先讲清楚的判断：

1. **换成 Markdown 不会变丑。** 好看来自 CSS，不来自 HTML 还是 Markdown。已经用**逐像素比对**证明过（文本层差 0 字符，视觉层 100% 相同，差异只落在新加的那个切换按钮上）。用户担心时，**做出来给他看，别争论**。
2. **用户说的"笔记没创意"和"我想改内容"往往是同一件事** —— 都是「在原文旁边长出一个子空间」。命名成**旁注**，一次解决两个需求。
3. **AI"从零写一段"远比"改一段"安全**。旁注是新增内容，错了不影响正文；重写正文要慎重。所以"点击 → AI 补一段 → 挂在原文旁"是优先级最高的 AI 能力。

原型外壳必须实证的两件事：**段落级标记**（低调，只表示"这段有注释"，不要序号——黄底数字圆点已被用户否决）和**词/句级落锚**（选中文字 → 浮按钮 → 生成的旁注把原文那几个字加虚线下划线）。后者是"锚在文字上而非段落上"最有说服力的证明。视觉裁决、晋升方案与 AI 接入的定稿见 shelf-and-marginnote.md §7。

## 踩坑清单

| 坑 | 现象 | 解法 |
|---|---|---|
| 高亮分两遍替换 | 代码块显示乱码/标签被染色 | 改单遍扫描（配方 1） |
| 表格用 `table-layout: fixed` + 百分比 | 形态多样的表格里长列被挤成 15% | 改 `table-layout: auto` + `.numcol` 工具类（配方 3） |
| `.kv th:first-child { width: 1% }` 单独使用 | `HTML` 竖成 H/T/M/L，一字一行 | 该技巧必须配 `white-space: nowrap`，否则别写 |
| 拼接脚本重跑 | 整批章节被插入两遍（section 数翻倍、id 出现 2 次） | 插入前断言目标 id 不存在（阶段 5） |
| 重建后补丁丢失 | 刚加的类名全没了（只剩 head 里的 CSS） | 重建后重跑补丁并复核计数（阶段 5） |
| 附录拼接顺序错 | B 排在 A 前面 | 合并后打印注释标记核对顺序 |
| `<pre>` 里的 HTML 未转义 | 代码块被浏览器当标签解析，内容消失 | 手写 `&lt;` `&gt;` `&amp;`。**用脚本批量检查**：抽出所有 `<pre><code>` 内容，找 `<(?=[a-zA-Z\/])` |
| `<script>` 里写 `</span>` | 无害（只有 `</script>` 会截断） | 正常写即可 |
| headless Chrome 带 `#anchor` 截图 | 输出纯空白页（锚点跳转在 headless 下不可靠） | **改用"只显示目标章节"的临时副本**：注入 `<style>.chapter:not(#ch21){display:none!important}</style>` 再截，比调锚点稳定得多 |
| 截图只能看到首屏 | 长章节后半段没法检查（如 69 行的属性全表） | `--window-size=1300,5200` 出长图，再 `sips --cropToHeightWidth <高> <宽> --cropOffset <y> 0` 裁切 |
| 声称"N 次""0 次"却没验证 | 书失去可信度 | 一律用 `grep -oh ... \| wc -l` 实测 |
| 加粗正则写 `\*\*([^*]+)\*\*` | 正文里的 `data-*` 会把 `*` 吃掉，此后所有加粗全部漏网 | 改 `\*\*([\s\S]+?)\*\*`。用"首尾公共前缀法"定位分歧点（见 shelf-and-marginnote.md §1） |
| 旁注圆点用"加边框"标记段落 | hover 时正文抖动重排 | 圆点改 `position: absolute; left: -34px`，段落 `position: relative`；阅读区左侧留 62px |
| 圆点绑定点击时把 note 闭包进去 | 新生成的旁注点不开（闭包里还是 `null`） | 点击时从 DOM 现读 `el.getAttribute("data-note")`，之后新建只要 `setAttribute` |
| 旁注面板表格用 `word-break: break-word` | `dataset` 被断成 `datase` / `t` | 表头 `white-space: nowrap`，单元格 `word-break: normal` |

### 做属性/接口审计时的三个必踩坑

如果要统计"某个属性/字段被谁生产、被谁消费"（这类审计结论最有说服力），务必注意：

1. **必须加属性名边界**。搜 `data-play` 会命中 `data-play-product`、`data-play-badge`。正确写法 `new RegExp(name + "(?![a-z0-9-])", "g")`。曾因漏这个边界，把"12 个冗余属性"误算成"11 个"，结论直接反向。
2. **模板字符串里的读取要单独扫**。把 JS 按字符串类型切片（反引号=模板/生产，单双引号=选择器/读取）时，`` `${el.dataset.benefitTitle}` `` 这种读取会被切进模板片。统计 `dataset.x` 时必须扫 `code + tpl` 两份，只扫 `code` 会漏。
3. **`setAttribute("data-xxx")` 检测不到**。切片时引号内容已被挪走，必须回到**原始文本**匹配。

审计脚本的通用纪律：**先用 2~3 个已知样本手工验证，再相信全量数字**。统计脚本自己出错，是这类结论最容易出的问题。

## 语气与表达

- 用**第二人称**："你看到的""你现在会..."
- 每章开头给一个**一句话目标**（"读完这章你会知道…"）
- 讲抽象概念时用**日常类比**，但不要幼稚化
- 有观点就说出来（"这个用法几乎可以当标准答案来抄""这是它容易被忽略的根本原因"）
- 避免"很简单""显然"——读者卡住时会觉得自己笨
- 不要在正文里堆 emoji；用带颜色的标签块（`<span class="card-tag">知识点</span>`）区分段落类型
